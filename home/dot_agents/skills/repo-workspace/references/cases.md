# Examples

These examples show how the rules in `SKILL.md` apply. Some come from the user's own repositories. The rules themselves stay in `SKILL.md`, and live state still decides each new case.

- **Talos, a contribution fork likely to be revisited.** The fork exists to send PRs to `siderolabs/talos`, and more source work there is expected. That makes it Contribute work at `Contribute/talos`, with a T3 project titled `siderolabs/talos`. The likely return is what justifies registering it. Its local `main` tracks `upstream/main`.
- **pkgs, a local-only patch.** A kernel option change in `siderolabs/pkgs` came with no-fork and no-push instructions. The work happens in the existing checkout, and those restrictions stay in force. No dedicated project was created, because nothing yet suggested a return or a need for native controls. A repeat source task would reopen that question. The planning lived in the Talos and home-lab conversations, but the edits happen in the pkgs checkout.
- **DigiKey MCP and SCBench, maintained downstreams.** Both are GitHub forks that the user maintains as their own variants. That makes them Personal, with `origin` and the baseline following the maintained line. An occasional fix sent upstream doesn't change that.
- **NuPhy, one vendor with several identities.** A maintained firmware variant, the user's tools, and private protocol research are all user-directed, so all three are Personal. Each keeps its own alias. The shared vendor didn't produce a vendor folder or merge their identities.
- **Home lab and Talos.** The home-lab repository is Personal infrastructure. When that work needed a change to Talos itself, the change belonged to the separate Contribute Talos checkout.
- **A design folder without Git.** A new keyboard-layout design is user-directed, so it is Personal, under a recognizable name. The Git top-level check has nothing to check, but the registration criteria still apply.
- **Reading a dependency versus keeping a reference.** Cloning libgit2 to answer one question is task scratch. A kernel tree kept around for grepping across many debugging sessions is Reference.
- **Linux.** The same categories appear as `personal`, `contribute`, and `reference` under that machine's existing root, such as `~/dev`. Neither the root nor existing aliases get renamed to match another platform.
- **Dotfiles.** `chezmoi source-path` reports `~/.local/share/chezmoi/home`, but the Git and T3 root is `~/.local/share/chezmoi`. The checkout stays where chezmoi manages it, with no second copy under Personal.
- **Two checkouts named talos.** A second Talos checkout arriving next to `Contribute/talos` is a conflict, not a duplicate. Comparing remotes, branches, and local-only work shows which variant each is. If both are kept, the newcomer gets a distinct alias agreed with the user, and the established checkout keeps its own.
- **A fork with no stated purpose.** A fork carrying three local commits could be a maintained variant or unsent contribution work, and its fork status alone can't tell which. The quickest resolution is one question to the user. Until they answer, the checkout gets no permanent home.
