# Worked cases

These cases show how the rules apply. They are examples, not a registry of this machine's repositories. Check live state before acting on any of them.

- **Contribution fork, likely to come back (Talos):** a fork exists so the user can send PRs to `siderolabs/talos`, and more source work there is expected. Place it at `Contribute/talos` and title the T3 project `siderolabs/talos`. The likely return justifies registering it. Local `main` tracks `upstream/main`.
- **Patch with no fork and no push (pkgs):** a kernel configuration change in `siderolabs/pkgs`, done under no-fork and no-push instructions. Work in the existing checkout and leave those restrictions in place. Don't create a dedicated project yet. Reconsider when there is an actual repeat source task or native controls become necessary. The motivating Talos or home-lab conversation can hold the planning, but the edits run in the pkgs checkout.
- **Maintained downstream that is technically a fork (DigiKey MCP, SCBench):** the user maintains their own variant. It is Personal, and `origin` and the baseline follow the maintained line. An occasional upstream PR from it does not make it Contribute.
- **Same vendor, separate identities (NuPhy):** a maintained keyboard firmware variant, the user's tools, and private protocol research are all Personal. Each keeps its own recognizable alias. A shared vendor doesn't create a vendor folder or merge their identities.
- **Personal infrastructure that changes upstream source (home lab):** the home-lab repository is Personal. A source change to Talos itself belongs in the Contribute Talos checkout, not in the home-lab repository.
- **Personal project without Git:** a design or research folder that isn't a repository lives under Personal with a recognizable name. The Git top-level check doesn't apply, but the registration criteria still do.
- **Reference or scratch:** a clone used only to read a dependency during one task goes in that task's scratch directory. Use `Reference` only for an independent source or build reference that is intentionally kept.
- **Platform casing:** on Linux the same categories are `personal`, `contribute`, and `reference`. Keep each machine's existing development root and existing aliases, case included. Platform style doesn't justify renaming anything, and this policy doesn't authorize moving any machine's repositories.
- **Dotfiles:** `chezmoi source-path` may be `~/.local/share/chezmoi/home` while the Git and T3 root is `~/.local/share/chezmoi`. Use the Git top-level. Keep its default branch, existing project, and worktrees. Don't make a second checkout under Personal.
- **Name collision:** `Contribute/talos` already exists when another Talos checkout appears. Treat it as a conflict. Check which variant each one is (remotes, branches, local-only work). If both must stay, give the newcomer a meaningful distinct alias that says which variant it is, and confirm it with the user. Don't rename the established checkout. Never overwrite either one.
- **Unclear role:** a fork with a few local commits and no stated purpose. Don't guess from fork status. Ask whether the user maintains it or is contributing it back. Until they answer, work read-only or in scratch.
